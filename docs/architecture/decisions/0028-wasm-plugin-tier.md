# 0028. The executable plugin tier: WebAssembly components, capability-gated and hard-limited

## Status

Proposed.
Implemented as task P8 of [the plugin host and icon themes plan](../plugin-host-and-icon-themes-plan.md), in `crates/plugin-host/src/wasm.rs`.
Extends [ADR-0026](0026-plugin-host.md), which decided the host and left the executable tier's own limits to this decision.
Answers the sandboxing half of [ADR-0001](0001-core-tech-stack.md)'s hybrid plugin system.

## Context

ADR-0026 built a plugin host with one tier: contributions that are data.
An icon theme is a mapping table and 904 SVGs, and it needs no code execution whatsoever.

That tier alone is not the plugin system ADR-0001 asked for, and it has a second problem: a host whose only contribution point is icon themes has never been shown to be a host.
So `contributes.commands` ships with this tier, as a second point with a real consumer — invoking a contributed command calls into the plugin's own code.

A plugin that runs code can do three things a manifest cannot:

- loop forever, and take the editor's UI with it;
- allocate until the process is killed;
- read files nobody meant it to read.

Each needs an answer, and "the plugin author will not do that" is not one — the point of a plugin system is that the author is a stranger.

`wit/plugin.wit` (ADR-0026, `plugin-api`) already fixed the shape of the seam: a WebAssembly component world with four host imports and three guest exports.
What was left open was the runtime, the limits, and what a denial looks like.

## Decision

**wasmtime, with the component model**, pinned to the feature set task P0 verified:

```toml
wasmtime = { version = "38", default-features = false, features = ["runtime", "cranelift", "component-model", "std"] }
```

Bindings are generated by `wasmtime::component::bindgen!` pointed at `plugin-api`'s `wit/` directory rather than at a copy.
The world lives with the contract, and generating from it makes a world that does not parse a build failure in `plugin-host` rather than a surprise at instantiation time.

### Three limits, because they catch three different failures

Each is per-`Store`, so they are per plugin and not per process, and each is re-armed per call — a plugin invoked a hundred times is not doing anything wrong.

- **Fuel** (`Config::consume_fuel`) bounds *work*.
  It is deterministic, it is charged per instruction, and it catches the ordinary runaway: a loop over a list longer than the author expected.
- **An epoch deadline** (`Config::epoch_interruption`) bounds *time*, with a watchdog thread bumping the epoch every 10 ms.
  Fuel alone is not sufficient and this is not belt-and-braces: fuel is only consumed by instructions Cranelift actually emitted, so a loop the optimiser folded — or a host call that blocks — can burn wall-clock without burning fuel.
  The watchdog is on another thread and does not care what the guest is doing.
  Conversely the epoch alone is not sufficient either: it is wall-clock, so it cannot distinguish a plugin doing far too much work from a machine that is merely busy, and its resolution is a tick.
- **A `StoreLimits` memory cap** bounds *space*, because neither of the other two stops a component from calling `memory.grow` in a straight line.

### A trap disables one plugin

Every guest call returns a `Result` on the host's side of the sandbox.
A trap — fuel, epoch, a refused `memory.grow`, or the plugin's own bug — is caught, converted to a typed `WasmError`, and the plugin's store is dropped, which frees its memory and makes "disabled but still resident" unrepresentable.
The editor and every other plugin keep running.

This is the property that justifies the whole tier, so it is tested rather than asserted: a trapping plugin and a working one are started together, the first is invoked, and the second is invoked afterwards and still works.

### Capabilities: deny, do not omit

The `Linker` provides all four host imports to every plugin.
What varies is what they do:

| Import | Gate |
|---|---|
| `log` | none |
| `notify` | `capabilities.notify` |
| `workspace-root` | `capabilities.workspace-root` |
| `read-file` | the path must resolve inside a prefix granted by `capabilities.read-files` |

A call the plugin was not granted returns `host-error::denied(<capability>)`.
It is deliberately *not* an absent import, which would fail at instantiation with a link error the plugin cannot see, catch or report.
A refusal that names the missing capability is something a plugin can log — and `log` needs no grant precisely so that it can.

`read-file` is checked three times, and each check answers something the others cannot:

1. **Lexically**, against the grant expanded relative to the plugin directory. Cheap, and the only check a built-in plugin — whose files are bytes in the binary — can make.
2. **After resolving symlinks**, against the same grant. A path with no `..` in it can still leave the granted prefix by pointing at one, and only a filesystem knows that.
3. **`LoadedPlugin::read_asset`**, which re-runs the relative-path rule and the plugin-directory containment check.

The third is not bypassed even though the first two subsume most of it: `read_asset` is the crate's single seam between a plugin-supplied string and a filesystem read, and a second, weaker copy of that check inside the host functions is exactly how such a seam stops being single.
The second is not redundant with it either — a symlink from `data/` to a sibling file stays inside the plugin directory, so `read_asset` would allow it while the grant does not.

### Quarantine markers are not written for this tier

`plugin-host` reads `<config_dir>/plugins/.quarantine/<id>` and refuses a plugin it names.
Writing markers was left open by ADR-0026; the conclusion here is **not to write any**.

The mechanism was designed in `syntax_core::runtime` for `dlopen`, where foreign native code can segfault the process before any error can be returned, so the only way to learn that a library is fatal is to record that you were about to load it.
A component cannot do that.
Compiling, instantiating and calling all return `Result` on the host's side of the sandbox, and every one of those failures is answered by disabling one plugin.
There is no window in which the editor dies with a plugin half-loaded, so there is nothing to mark, and a marker written around a window that cannot kill anyone would be a file the user has to delete for no reason.
The read path stays: a user can still quarantine a plugin by hand, and a future tier that does run native code would write markers around exactly its own window and no wider.

## Consequences

- `plugin-host` gains wasmtime and about 40 MB of dependency tree; `docs/architecture/layering.md`'s row for it says so. Every other crate is unaffected, which is the point of ADR-0026's two-crate split — reading a manifest still costs `serde` and `toml`.
- One extra thread for the process, sleeping on a 10 ms tick.
- Plugin commands are a mechanism from this task on; wiring them into the palette is P5–P7's job.
- The manifest's capability vocabulary is now load-bearing at runtime, so widening it is an `api_version` question rather than a convenience.
- Guest calls are synchronous and run on the caller's thread. A plugin cannot hang the editor for longer than its deadline, but it can occupy the caller for that long; moving invocation off the UI thread is a later change this design does not prevent.

### The Windows cross-build, and the escape hatch

`x86_64-pc-windows-gnu` is Tier 2 upstream and therefore not covered by wasmtime's release gating, which made "does the Cranelift backend link through MXE" the risk that had to be retired before this task could exist.
Task P0 answered it: wasmtime 38.0.4 with the feature set above cross-builds **and links** through `ide-windows-builder`, and this task re-verified it after actually adding the dependency.
Runtime behaviour is verified natively on Linux; the Windows binary is link-checked only, because the build host cannot execute it.

If a future wasmtime release regresses that target, the documented escape hatch is the **Pulley interpreter backend** — pure Rust, no native codegen, no platform-specific linking — by swapping `cranelift` for `pulley` in the feature list.
It is slower and nothing else changes: the same component model, the same limits, the same host functions.
It is not used today because it is not needed today.

### Rejected alternatives

**ADR-0001's native dylib tier (`dlopen`, a stable C ABI).**
Cheaper, faster, and the machinery already exists in `syntax_core::runtime` — including the quarantine markers, which exist *because* that tier can take the process down.
Rejected for third-party plugins for exactly that reason: the property that a bad plugin disables itself and nothing else cannot be had from a native dylib at any price.
The trade-off was accepted for foreign tree-sitter grammars, where there is no alternative; for plugins there is one.
Nothing here forbids adding the tier later for trusted, performance-critical extensions — it would be a new optional manifest section and an `api_version` bump.

**Fuel alone, or the epoch alone.**
Each misses what the other catches; see the limits above.
Two mechanisms with a comment saying why is cheaper than one mechanism plus an incident.

**Omitting an ungranted import instead of denying it.**
Smaller host code, and it fails earlier — at instantiation.
Rejected because it fails *opaquely*: the plugin gets a link error it cannot catch, the user gets "this plugin does not work", and nobody learns which line of `plugin.toml` was missing.

**Async host calls and a guest executor.**
The world has no async in it, `notify` and `read-file` are both fast, and `default-features = false` drops the async machinery — which is part of what keeps the Windows link within reach.

**Compiling the example plugin in CI.**
A worked example lives at `crates/plugin-host/examples/hello-plugin/`, with its own `[workspace]` table so the parent workspace does not adopt it, and a documented build command.
Building it in CI needs a `wasm32-unknown-unknown` target and `wasm-tools` in `docker/Dockerfile`, which would cost every build for one file.
The tier is tested instead by small components written inline in the component-model text format — which is a genuinely stronger test than an example that merely compiles, because a text component can be made to spin, trap, or ask for a file it was not granted.
